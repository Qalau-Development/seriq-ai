# Локальный стенд: бэкенд с аккаунтами для сайта и приложения

Одна команда поднимает бэкенд в режиме `mock` с аккаунтами и историей на временной базе. Для разработки входа, истории и сводки прогресса; боевой сервер и его базу трогать не нужно.

## Запуск

Из корня репозитория (нужны зависимости бэкенда в `.venv`: `uv venv --python 3.12 .venv && uv pip install -r backend/requirements.txt`):

```bash
bash infrastructure/scripts/dev-backend.sh
```

Скрипт сам применяет миграции к временной базе SQLite в `/tmp`, создаёт случайный `SERIQ_AUTH_SECRET` (`openssl rand -base64 48`, в журнал не печатается и нигде не сохраняется), запускает бэкенд на `http://localhost:8000` и печатает адреса для сайта и приложения. После `Ctrl+C` временная папка с базой удаляется: каждый запуск начинается с пустой базы, пользователи не сохраняются.

Другой порт: `PORT=8001 bash infrastructure/scripts/dev-backend.sh`. Другой Python (например, окружение вне репозитория): `PYTHON=/путь/к/python bash infrastructure/scripts/dev-backend.sh`.

Проверка: `curl -s localhost:8000/api/v1/health` должен вернуть `{"status":"ok","mode":"mock","version":"0.1.0","database":"ok"}`. Поле `database` показывает, что аккаунты включены: по нему клиенты решают, показывать ли вход.

В режиме `mock` анализ видео возвращает тестовые ответы (`mock_scenario=complete|incomplete|uncertain|no_pose`), так что для проверки входа и истории настоящая модель не нужна.

## Сайт

```bash
cd apps/web
SERIQ_API_PROXY=http://localhost:8000 npm run dev      # http://localhost:3000
```

`/api` сайт передаёт бэкенду через прокси разработки; порт 8000 используется по умолчанию, переменную достаточно задать, если вы запустили бэкенд на другом порту.

**Safari:** refresh-токен сайта лежит в cookie `seriq_refresh` с флагом `Secure`. Safari не сохраняет такие cookie по `http://localhost`, поэтому вход после перезагрузки страницы там не удержится. Для разработки используйте Chrome (там `localhost` считается безопасным адресом) или открывайте сайт по `https`.

## Приложение

```bash
cd apps/mobile
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8000/api/v1      # Android-эмулятор
flutter run --dart-define=API_BASE_URL=http://localhost:8000/api/v1     # iOS-симулятор
```

- `10.0.2.2` в Android-эмуляторе означает компьютер, на котором он запущен. На реальном телефоне в той же сети используйте адрес компьютера в этой сети и запускайте скрипт с доступом извне: по умолчанию бэкенд слушает только `127.0.0.1`.
- В репозитории в манифестах Android и в `Info.plist` iOS открытый HTTP **не разрешён** (нет `usesCleartextTraffic` и исключений ATS). Android 9 и новее, а iOS без исключения такие запросы блокируют. Это настройка приложения (`apps/mobile`), в этом стенде её нет и проверить её без запуска приложения я не мог: если вход по HTTP не проходит, причина, скорее всего, в ней.

## Что сбрасывается и что нет

- Пользователи и история живут, пока работает скрипт. Перезапуск начинает с чистой базы.
- Лимиты входа и регистрации по IP считаются в памяти процесса: перезапуск скрипта их тоже сбрасывает (20 попыток входа за 10 минут и 5 регистраций в час с одного адреса, см. раздел «Accounts and history» в [api.md](../api.md)).
- Секретов в репозитории нет: ключ создаётся при каждом запуске заново.
