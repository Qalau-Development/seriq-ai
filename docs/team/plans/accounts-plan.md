# Проект: аккаунты и хранение данных (этап 2)

Статус: **рабочий файл, ничего не реализовано.** Здесь варианты и решения «берём / не берём». В конце проекта файл удаляется. Публичное описание сделанного ведётся отдельно в [privacy-and-security.md](../../privacy-and-security.md), и только по факту.

Решение руководителя: **вход только по логину и паролю.** Входа через Google, Apple и другие сторонние сервисы не делаем и не планируем.

Что есть сейчас: аккаунтов и базы нет, видео удаляется сразу после анализа, история занятий лежит на устройстве (ключ `seriq.sessions.v1`, у занятия локальный UUID, у попытки `analysis_id`). Что хотим: регистрация и вход, профиль, облачное сохранение занятий (local-first, без дублей), удаление аккаунта и данных, гостевой режим.

Рамки, которые не меняются: видео и кадры не храним никогда; корректирующих медицинских указаний нет; контракт API меняется только добавлением; анализ (`POST /analysis`) остаётся доступным без входа.

## 1. Что храним

Только результат анализа и данные для входа. Не храним: видео, кадры, `pose` (точки кисти), `angle_series`, IP-адрес, данные устройства, email.

```text
users
  id                  uuid, PK
  login               text, NOT NULL      -- как ввёл пользователь, для показа
  created_at          timestamptz
  password_hash       text, NOT NULL      -- argon2id, соль и параметры внутри строки
  password_changed_at timestamptz         -- токены, выданные раньше, недействительны
  display_name        text, null          -- необязательно, для приветствия
  locale              text, null          -- 'ru' | 'kk' | 'en'
  UNIQUE INDEX ON (lower(login))          -- уникальность без учёта регистра

refresh_tokens
  id              uuid, PK
  user_id         uuid -> users, ON DELETE CASCADE
  family_id       uuid                    -- цепочка ротации
  token_hash      bytea, UNIQUE           -- SHA-256 от случайного токена
  expires_at      timestamptz
  used_at         timestamptz, null       -- повторное использование = кража, вся семья отзывается
  revoked_at      timestamptz, null

login_failures                            -- счётчик неудачных входов по логину, без IP
  login_key       text, PK                -- lower(login), есть и для несуществующих логинов
  failed_count    int
  blocked_until   timestamptz, null
  updated_at      timestamptz             -- старые строки чистятся

recovery_codes                            -- только если примем коды восстановления (раздел 2)
  id, user_id -> users ON DELETE CASCADE, code_hash bytea, used_at

sessions                                  -- «занятие»
  id              uuid, PK                -- локальный UUID с устройства
  user_id         uuid -> users, ON DELETE CASCADE
  exercise        text                    -- 'E01'..'E04'
  started_at      timestamptz             -- время с устройства
  created_at      timestamptz             -- время получения сервером

attempts                                  -- «анализ» внутри занятия
  analysis_id     uuid                    -- как в ответе POST /analysis
  user_id         uuid -> users, ON DELETE CASCADE
  session_id      uuid -> sessions, ON DELETE CASCADE
  at              timestamptz
  source          text                    -- 'mock' | 'model'
  model_version   text
  verdict         text                    -- 'completed' | 'check_instructions'
  label           text                    -- 'complete' | 'incomplete' | 'uncertain'
  confidence      real
  measure_name    text
  measure_unit    text
  measure_value   real, null
  measure_series  jsonb, null             -- {fps, values}; до ~600 чисел на попытку
  PRIMARY KEY (user_id, analysis_id)

deleted_sessions                          -- «надгробия», чтобы удалённое занятие не вернулось со второго устройства
  user_id, session_id, deleted_at         -- PK (user_id, session_id)
```

Оценка объёма: попытка ≈ 3–6 КБ вместе с рядом. 10 000 попыток ≈ 50 МБ. Бесплатного тарифа хватает с запасом.

Решение по ряду: храним `measure_series`, чтобы график открывался в истории после смены телефона. Если окажется, что не нужен, колонка убирается миграцией, остальное не меняется.

Доверие к данным: клиент сам присылает результат, сервер не может проверить, что он настоящий. **Не берём** подпись результата при анализе (HMAC от сервера): данные видит только владелец, подделка вредит только ему. Риск принят. Серверная валидация остаётся: формат, диапазоны (`confidence` 0–1, число значений ряда не больше 1000), набор меток.

## 2. Регистрация, вход и гостевой режим

### Что использовать как логин

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Имя пользователя** (не email) | минимум данных: ничего, что связывает аккаунт с человеком; нет рассылок и утечки почты | **нет восстановления пароля по почте**; пользователь может забыть логин |
| B. Email | восстановление пароля письмом; знакомо людям | хранится персональный идентификатор; нужна почтовая служба (отправка, доставляемость, письма не в спаме), подтверждение адреса, защита от перебора адресов; больше кода и больше ответственности |

**Рекомендация: вариант A.** Для учебного проекта и для минимума данных. Правила логина: 3–32 символа, латинские буквы, цифры, `.`, `_`, `-`; только ASCII, чтобы не было визуально одинаковых логинов из разных алфавитов; хранится как введён, сравнивается через `lower(login)`. В форме подсказка: «не используйте настоящее имя или почту».

Последствия варианта A и что с ними делать:

- Забытый пароль нельзя вернуть письмом. Но история **не пропадает вместе с аккаунтом**: она хранится и на устройстве (local-first). Пользователь регистрирует новый аккаунт и переносит локальную историю (идемпотентно, как при переносе гостя). Потеряется только то, что было на других устройствах и уже стёрто с них.
- Что можно добавить поверх:
  1. **Коды восстановления** (рекомендую как необязательный шаг): при регистрации показываем 5 одноразовых кодов по 12 символов (алфавит без похожих знаков, ≈ 60 бит), пользователь сохраняет их сам; на сервере только SHA-256 от кода (код случайный и длинный, медленный хэш не нужен). `POST /auth/recover` с логином, кодом и новым паролем; код сгорает, остальные остаются; все refresh-токены отзываются. Минус: ещё один экран и ответственность пользователя (для людей после инсульта это нагрузка), поэтому шаг можно пропустить.
  2. Только смена пароля при входе (`POST /me/password`), забытый пароль = новый аккаунт и перенос локальной истории. Проще всего, ничего не нужно хранить.
- Решение за руководителем (раздел 8). Если коды не берём, строки `recovery_codes` и `/auth/recover` убираются, остальное не меняется.

### Пароль

Правила (проверяет сервер, клиент только подсказывает):

- длина **10–128 символов**; нижний предел задаёт защиту от угадывания, верхний защищает от нагрузки при хэшировании (длинная строка = лишняя работа);
- **без обязательных «цифр и символов»** и без принудительной смены по расписанию: такие правила не повышают надёжность, а нашим пользователям (после инсульта, часто с одной рабочей рукой) набирать сложнее; разрешаем вставку из менеджера паролей, кнопка «показать пароль», любые Unicode-символы;
- пароль не может совпадать с логином (без учёта регистра) и не может содержать его целиком;
- простая проверка по короткому списку самых частых паролей (порядка 1000 строк, файл в репозитории), берём, если хватит времени;
- ответ `400 weak_password` с кодом и с понятным текстом для клиента, какое правило нарушено; сам пароль в ответ **не возвращается**.

### Хэш пароля: argon2id

- Библиотека `argon2-cffi`, алгоритм argon2id. Соль случайная, внутри строки хэша, отдельной колонки нет.
- Параметры под бэкенд с лимитом 2 ГБ, где одновременно может идти анализ видео: стартуем с **память 64 МиБ, 3 прохода, 1 поток** (профиль, близкий к рекомендациям RFC 9106 для ограниченной памяти). Цель: 150–300 мс на хэш **на нашем сервере**. На этапе 3 замерить время и память прямо на VPS и подобрать. Не подбирать на ноутбуке.
- Одновременно считается не больше 2 хэшей (семафор): пик ≈ 128 МиБ. Остальные запросы ждут, при длинной очереди отвечаем 503 `busy`, как и анализ. Иначе всплеск входов даст нехватку памяти у анализа. Допустимый пик проверить рядом с анализом на сервере.
- Перехэширование: после успешной проверки `check_needs_rehash`; если параметры сервера новее, хэш тихо заменяется новым.
- Пароль никогда не пишется в логи и не возвращается ни в одном ответе. Для этого: свой обработчик ошибок проверки тела на роутах `/auth` и `/me` (сейчас общий обработчик в `main.py` отвечает на любую ошибку проверки как `missing_video`, это нужно разделить), ошибки не логируют вход, тела запросов не логируются.
- «Перец» (секретная добавка из окружения) не берём сейчас: даёт мало, добавляет ключ, потеря которого ломает все входы.

### Вход, ошибки и защита от перебора

- Ответ на неверный логин и на неверный пароль **одинаковый**: `401 invalid_credentials`, то же сообщение, та же форма.
- **Постоянное время**: если логина нет, сервер всё равно считает argon2id по заранее вычисленному фиктивному хэшу. Иначе по времени ответа видно, существует ли логин.
- **Лимит по логину** (в таблице `login_failures`, а не в памяти, чтобы переживал перезапуск): после 5 неудач подряд растущая задержка (1, 2, 4 … до 15 минут), ответ `429 rate_limited` с `Retry-After`. Это сделано по логину, **а не по IP**, и счётчик ведётся и для несуществующих логинов, чтобы нельзя было различить их. Жёсткая блокировка аккаунта не берётся: её можно использовать, чтобы закрыть чужой аккаунт, поэтому только задержка. Счётчик сбрасывается после успешного входа.
- **Лимит по IP** (в памяти процесса, на диск и в БД IP не пишется): порядка 20 попыток входа и регистраций за 10 минут. Работает при одном воркере (`--workers 1`, как сейчас); при нескольких воркерах нужен общий счётчик.
- **Важно про IP**: перед бэкендом стоят Traefik и Caddy. Без настройки доверенных прокси бэкенд увидит один и тот же адрес у всех, и лимит по IP заблокирует всех сразу. Нужно брать адрес клиента из `X-Forwarded-For` только от наших прокси; проверить на сервере на этапе 3.
- Регистрация: `409 login_taken` неизбежно показывает, что логин занят (иначе нельзя зарегистрироваться). Ограничено лимитом по IP, порядка 5 регистраций в час с адреса.
- Все числа выше — стартовые, настраиваются через окружение; окончательные согласует руководитель (раздел 8).

### Токены (как планировалось, без изменений)

Access: JWT, 15 минут, подпись HS256 ключом из окружения. Refresh: случайные 256 бит, в БД только SHA-256-хэш, 30 дней, ротация при каждом использовании, повторное использование отзывает всю семью. Сайт: refresh в httpOnly Secure SameSite=Strict cookie (сайт и API на одном домене), access в памяти. Приложение: `flutter_secure_storage`. Проверка защищённых запросов дополнительно сравнивает `iat` токена с `password_changed_at`: после смены пароля старые access-токены перестают работать сразу, а не через 15 минут.

### Гостевой режим (берём)

Без входа всё работает как сейчас: анализ, история на устройстве. Аккаунт добавляет облако, ничего не отнимает.

Перенос гостевой истории **при регистрации и при входе** (тот же механизм):

1. После регистрации или входа клиент спрашивает: «Перенести историю с этого устройства в аккаунт?».
2. При согласии отправляет локальные занятия через `POST /sessions/import` (до 100 за запрос, до 200 попыток в занятии).
3. Успешно отправленные занятия помечаются на устройстве как синхронизированные (поле `synced_at`, расширение формата, старые клиенты его игнорируют).
4. Если на устройстве уже были занятия другого аккаунта: владелец локальной истории хранится рядом (`owner`: `null` = гость, иначе id пользователя); чужую историю не показываем и не отправляем.
5. При выходе спрашиваем: оставить локальную историю или стереть с устройства.

## 3. API

Все новые эндпоинты под `/api/v1`, ошибки в прежнем формате `{"status":"error","error":{"code","message"}}`. Защищённые принимают `Authorization: Bearer <access_token>`. Описание в `docs/api.md` дописывается отдельным PR после согласования с Zenki-Erzat; до этого это предложение.

| Метод и путь | Назначение |
|---|---|
| `POST /auth/register` | `{login, password, display_name?, locale?}` → 201 `{access_token, refresh_token, expires_in, user}`; сразу вход |
| `POST /auth/login` | `{login, password}` → то же |
| `POST /auth/refresh` | `refresh_token` → новая пара (ротация); для сайта берётся из cookie |
| `POST /auth/logout` | отзывает текущую семью refresh-токенов |
| `POST /auth/recover` | `{login, recovery_code, new_password}`; только если примем коды |
| `GET /me` | профиль: `id`, `login`, `display_name`, `locale`, `created_at` |
| `PATCH /me` | `display_name`, `locale` |
| `POST /me/password` | `{current_password, new_password}`; меняет пароль, **отзывает все refresh-токены**, возвращает новую пару для этого устройства |
| `DELETE /me` | `{password}` подтверждает, удаляет аккаунт и все данные, ответ 204 |
| `PUT /sessions/{session_id}` | идемпотентно создаёт или дополняет занятие с попытками |
| `POST /sessions/import` | то же для пачки занятий (перенос гостевой истории) |
| `GET /sessions?cursor=` | список занятий постранично, новые первыми |
| `GET /sessions/{session_id}` | занятие с попытками |
| `DELETE /sessions/{session_id}` | удаляет занятие, ставит «надгробие» |
| `DELETE /sessions` | удаляет всю историю, аккаунт остаётся |

### Идемпотентность и отсутствие дублей

- Ключи задаёт клиент: `session_id` (локальный UUID занятия) и `analysis_id` (UUID из ответа анализа). Серверный id не нужен.
- `PUT /sessions/{id}`: тело содержит занятие и список попыток. Занятие создаётся при первом запросе. Попытки добавляются так: `INSERT ... ON CONFLICT (user_id, analysis_id) DO NOTHING`. Попытка после записи не меняется.
- Повтор того же запроса (обрыв сети, повторная отправка) возвращает 200 и то же состояние. Новые попытки в уже существующем занятии добавляются, старые не трогаются.
- Занятие, удалённое на другом устройстве: `session_id` из `deleted_sessions` → 409 `session_deleted`; клиент удаляет его у себя.
- `session_id` или `analysis_id`, уже принадлежащие другому пользователю, → 409 `id_conflict` (без подробностей).
- Синхронизация клиента: отправка после каждой попытки в фоне; при неудаче остаётся в очереди и уходит при следующем запуске. Сервер не требует порядка.

### Коды ошибок (добавляются к существующим)

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `invalid_request` | тело не прошло проверку формата, в том числе формат логина |
| 400 | `weak_password` | пароль не прошёл правила (длина, совпадение с логином, частый пароль) |
| 401 | `invalid_credentials` | вход: неверный логин **или** пароль, ответ один и тот же |
| 403 | `invalid_credentials` | пароль-подтверждение в `/me/password` или `DELETE /me` неверный; 403, а не 401, чтобы клиент не принял это за истёкший вход |
| 401 | `invalid_token` | токена нет, подпись неверна, токен отозван или выдан до смены пароля |
| 401 | `token_expired` | access-токен истёк, клиент делает refresh |
| 401 | `refresh_reused` | refresh использован повторно, все сессии отозваны, нужен новый вход |
| 404 | `not_found` | занятия нет у этого пользователя |
| 409 | `login_taken` | логин занят (регистрация) |
| 409 | `session_deleted` | занятие удалено на другом устройстве |
| 409 | `id_conflict` | идентификатор занят другим пользователем |
| 413 | `payload_too_large` | слишком много занятий или попыток в запросе |
| 429 | `rate_limited` | слишком частые попытки входа, регистрации или синхронизации; есть `Retry-After` |

### Удаление аккаунта

`DELETE /me` с паролем в одной транзакции удаляет `users`, а с ним `refresh_tokens`, `recovery_codes`, `sessions`, `attempts` (каскад), `deleted_sessions` и запись в `login_failures`. Физическое удаление, без «мягкого». Неверный пароль считается неудачной попыткой входа (общий счётчик по логину). После удаления токены недействительны. Клиент стирает локальные токены и спрашивает про локальную историю. Остаток: копии в бэкапах живут до конца их срока хранения (см. раздел 4); срок указываем пользователю.

## 4. База данных

Требование: PostgreSQL **отдельно от VPS с моделью**. Там 4 ГБ: бэкенд ограничен 2 ГБ, сайт 512 МБ, плюс Dokploy и Traefik, и анализ видео требует запаса. Postgres рядом ради 256–512 МБ оставит слишком мало на пик анализа.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Управляемая БД (managed Postgres у облачного провайдера, есть бесплатные и дешёвые тарифы) | ничего не администрируем; TLS и шифрование диска и бэкапы входят; быстрее всего | данные в чужом облаке, регион проверить; бесплатные тарифы могут усыплять базу и ограничены по размеру: условия сверить в момент выбора |
| B. Второй небольшой VPS с Postgres в Docker (через Dokploy) | полный контроль, данные в выбранном регионе | сами настраиваем TLS, firewall, бэкапы, обновления; шифрование диска зависит от провайдера; ещё один сервер платить и обслуживать |
| C. Postgres на том же VPS | проще всего | противоречит требованию, риск для анализа, один сбой выводит из строя всё |

**Рекомендация: вариант A** для учебного проекта: меньше всего ручной работы, а шифрование на диске, TLS и бэкапы получаем без своих усилий. Вариант B запасной, если A не подойдёт по региону или условиям. C не берём. Теперь в базе лежат ещё и хэши паролей, поэтому защита базы важнее: см. раздел 5.

Стек:

- SQLAlchemy 2.0, синхронный движок и драйвер psycopg 3: роуты бэкенда сейчас обычные `def`, асинхронность не нужна. Пул 2–5 соединений.
- Alembic: миграции в репозитории, `alembic upgrade head` запускается в `deploy.sh` до старта нового бэкенда. Откат в `deploy.sh` возвращает код, не схему, поэтому миграции делаем совместимыми назад (сначала добавляем, потом убираем).
- Строка подключения `SERIQ_DATABASE_URL` только в `.env` на сервере, `sslmode=verify-full`.
- Тесты: Postgres как сервис в GitHub Actions, чтобы типы (`jsonb`, `uuid`) вели себя как на сервере; в локальной разработке тот же контейнер. Входа «для разработки» в обход пароля нет: тесты и мок-режим создают пользователей через `/auth/register`, как обычные клиенты.
- Если база недоступна: `/analysis` продолжает работать (он от БД не зависит), `/health` показывает состояние БД отдельным полем (новое необязательное поле).

## 5. Шифрование и защита: берём / не берём

| Пункт | Решение | Почему |
|---|---|---|
| TLS на входе (HTTPS) | **берём, обязательно**; уже есть | пароль уходит на сервер только по HTTPS. Сейчас Traefik + Let's Encrypt, TLS 1.3, HTTP → 301 на HTTPS. Клиенты обращаются только по `https://` (в приложении запретить открытый HTTP, проверить на этапе 4); отдаёт ли Traefik заголовок HSTS, проверить и при необходимости включить |
| TLS до базы | **берём** | `sslmode=verify-full`, сертификат провайдера в образе; без TLS не подключаемся |
| Хэш пароля argon2id | **берём** | см. раздел 2; пароль в открытом виде нигде не хранится и не логируется |
| Защита от перебора и постоянное время ответа | **берём** | раздел 2; без этого пароли подбираются |
| Шифрование диска или тома БД | **берём через вариант A**: шифрование «at rest» у провайдера. Для варианта B зависит от провайдера (LUKS на VPS требует отдельной установки), тогда не берём сейчас | в managed-вариантах включено по умолчанию, нужно только убедиться в документации провайдера и записать это |
| Access-токен | **берём**: JWT, срок 15 минут, подпись HS256 ключом из окружения (`kid` в заголовке для ротации) | один сервис, внешнему проверяющему ключ не нужен; короткая жизнь ограничивает ущерб |
| Refresh-токен | **берём**: случайные 256 бит, в БД только SHA-256-хэш, срок 30 дней, ротация при каждом использовании, повторное использование отзывает всю семью; смена пароля отзывает все | медленный хэш (argon2) не нужен: токен случайный и длинный |
| Хранение токенов у клиента | **берём**: сайт — refresh в httpOnly Secure SameSite=Strict cookie, access в памяти; мобильное — `flutter_secure_storage` (Keychain, Keystore) | токен недоступен скриптам страницы |
| Секреты только в окружении сервера | **берём** | уже так: `.env` вне репозитория; ключ подписи, `SERIQ_DATABASE_URL` только там и в GitHub Actions secrets |
| Шифрование полей на уровне приложения | **не берём сейчас** | см. ниже |
| Зашифрованные резервные копии | **берём через вариант A** (бэкапы провайдера шифруются at rest, срок хранения записать, например 7 дней). Свои дампы с `age` **не берём сейчас** | свои бэкапы = свой ключ, своё хранилище и проверка восстановления; пока лишнее |
| Проверка восстановления из бэкапа | **берём** один раз до выпуска | бэкап, который ни разу не восстанавливали, бэкапом не считается |
| Перец для паролей | **не берём** | почти ничего не добавляет к argon2id, но добавляет ключ, потеря которого ломает все входы |
| Двухфакторная аутентификация | **не берём** | сверх задачи; для людей после инсульта лишняя нагрузка |
| Логи без секретов | **берём** | не писать пароли, токены, коды восстановления, тела запросов и результаты |

### Шифрование полей: что рассматривали

Если бы брали: AES-256-GCM (библиотека `cryptography`), случайный nonce 96 бит на значение, формат `kid || nonce || ciphertext || tag`, ключ `SERIQ_DATA_KEY` (32 байта) только в окружении сервера, `kid` позволяет вводить новый ключ и перешифровывать постепенно. Что шифровать: `measure_series`, возможно `display_name`.

Почему не берём сейчас:

- ключ лежит на том же сервере, что и приложение: защищает от утечки дампа или бэкапа, но не от взлома сервера;
- шифрованные ряды нельзя фильтровать и агрегировать в БД, а нам это в перспективе нужно;
- потеря или ошибка ключа = потеря данных; нужен процесс ротации и хранения ключа;
- данные малы по значению для постороннего: без email и настоящего имени ряд чисел ни к кому не привязан (при условии, что логин не содержит настоящее имя, поэтому подсказка в форме).

Возвращаемся к вопросу, если появятся более чувствительные поля. Тогда: шифруем именно их, ключ в секретном хранилище провайдера, а не в `.env`.

## 6. Минимизация данных

Не собираем и не храним: email, телефон, адрес, диагноз, возраст, дату рождения, пол, вес и рост, фото, видео, кадры, точки кисти, геолокацию, идентификаторы устройства и рекламные идентификаторы, IP-адрес в базе, свободный текст (заметок к занятию нет, чтобы туда не попадали диагнозы). Аналитики и сторонних трекеров в приложениях нет, и мы их не добавляем.

Что собираем и зачем:

| Поле | Зачем |
|---|---|
| логин | войти в аккаунт |
| хэш пароля | проверить пароль; сам пароль не хранится |
| имя (необязательно) | приветствие на экране |
| язык интерфейса | показывать приложение на нужном языке |
| результаты анализа | история занятий на любом устройстве |
| счётчик неудачных входов (по логину) | защита от перебора; сбрасывается и чистится |

Открыто: журналы доступа прокси (Traefik/Dokploy) могут содержать IP-адреса запросов. Что и как долго они пишут, не проверялось; проверить на сервере и записать в публичный документ, когда будет известно. Сам бэкенд IP в базу не пишет.

## 7. Правила магазинов приложений

Это не юридическая консультация, формулировки магазинов меняются: **сверить актуальные тексты перед выпуском.**

- Правило App Store о том, что при входе через сторонние сервисы нужно предлагать и вход через Apple, относится к приложениям, которые предлагают такой сторонний вход. У нас его нет: только свой логин и пароль. Поэтому это правило нас, по нашему пониманию, не касается.
- Обратное верно для удаления аккаунта: если в приложении можно создать аккаунт, магазины ждут возможность удалить его из самого приложения (App Store так требует, у Google Play есть похожее требование и просьба указать ссылку на удаление данных). `DELETE /me` и экран «Удалить аккаунт и данные» в плане есть; ссылку для Google Play решить на этапе 4.

## 8. Порядок работ (этапы 3–5)

Оценка в часах на одного разработчика, с запасом на согласование. Реальные сроки зависят от того, что уже сделано до конкурса. Всё считается как код и тесты: регистрация, лимиты, хэширование и смена пароля пишутся и проверяются нами, внешних сервисов и их настройки нет, поэтому нет и ожидания чужих согласований.

### Этап 3. База и сервер (№3, помощь №2 с инфраструктурой)

| Шаг | Объём |
|---|---|
| Выбрать и завести БД (вариант A), TLS, переменные окружения, секреты в GitHub | 2–3 ч |
| SQLAlchemy-модели, Alembic, первая миграция, Postgres в CI | 3–4 ч |
| Регистрация, вход, refresh, logout: argon2id с семафором, фиктивный хэш, перехэширование, токены, разделение обработчика ошибок | 6–7 ч |
| Лимиты: по логину (БД), по IP (память), настройка доверенных прокси и проверка на сервере | 3–4 ч |
| `/me`, смена пароля с отзывом токенов, удаление аккаунта с паролем | 3–4 ч |
| Занятия: `PUT`, `import`, список, удаление, «надгробия», идемпотентность | 5–6 ч |
| Тесты: авторизация (одинаковый ответ, повторное использование refresh, лимиты, смена пароля), повтор запроса, гонка двух устройств | 5–6 ч |
| Замер времени и памяти argon2id на VPS, подбор параметров | 1–2 ч |
| Деплой: миграции в `deploy.sh`, проверка отката | 2 ч |
| Дополнение `docs/api.md` отдельным PR | 1–2 ч |
| *Если примем коды восстановления:* генерация, `/auth/recover`, тесты | +3–4 ч |

Итого около 31–40 ч (в прошлой редакции плана с внешним входом было 22–28 ч: там проверка токена была вызовом библиотеки, а здесь регистрация, лимиты и смена пароля пишутся нами). Риски: память argon2id рядом с анализом на VPS (проверить пик); лимит по IP при неверной настройке прокси блокирует всех; миграция и откат деплоя; бесплатный тариф БД с ограничениями.

| Шаг | Объём |

## 9. Что решить руководителю

1. **Логин:** имя пользователя без email (рекомендую) или email. Email даёт восстановление письмом, но это почтовая служба, хранение адреса и больше кода.
2. **Коды восстановления** при регистрации (рекомендую как необязательный шаг, +7–8 ч всего) или только смена пароля при входе (забытый пароль = новый аккаунт и перенос локальной истории с устройства).
3. **Политика лимитов:** стартовые значения (5 неудач по логину и растущая задержка до 15 минут; 20 попыток в 10 минут и 5 регистраций в час по IP) или другие.
4. **Длина пароля:** от 10 символов (рекомендую) или другая.
5. **Провайдер и регион БД:** вариант A (рекомендован) или B.
6. Берём ли ряд (`measure_series`) в облако или хватит итоговых полей.
7. Срок хранения бэкапов и что сообщаем пользователю об остатке в бэкапах после удаления.
8. Не сливать этап 3 в `main` без согласованного времени: меняется сервер.
